## A. 使用說明書

### A1 系統分層（誰負責什麼）

| 層 | 元件 | 職責 |
|---|---|---|
| 資料層 | `npm run analyze:replay`（`tools/analyze-saved-replay.ts`） | 巨觀戰報／triage 篩關鍵手／`--board` 盤面還原／`--coach` PIMC 逐手掃描／`--anchor` 一致率回寫 |
| 判斷層 | `replay-review` skill（模型本人） | 讀資料層輸出，做單手決策深掘、替代線對照、下定論 |
| 記憶層 | `reports/NN_*.md`＋`reports/lessons/`＋`INDEX.md` | 跨場教訓（「你上次也這樣」）；L0007/L0008 是【AI行為】類，提醒分析者引擎的已知偏差 |
| 錨點層 | `data/human-anchor/matches.jsonl`＋`npm run anchor:trend`＋`npm run ladder:policy` | 人機一致率/blunder 隨 engineVersion 的趨勢；AI 強度的兩把尺 |
| 主軸層 | `data/gameplans/profiles.json`（`src/ai/gameplan.ts`） | 牌組戰略主軸的進度追蹤，餵給巨觀戰報「主軸覆盤」與 coach 的 tone/badges |

### A2 指令速查（含本次新用法）

```bash
# 單場巨觀戰報（快，~2s）：Set 走向、失Set歸因、事件/技能效率、主軸覆盤
npm run analyze:replay -- --file=data/replays/<檔>.json

# 篩關鍵手（快）；折入 PIMC 噪訊判斷加 --coach
npm run analyze:replay -- --file=... --triage [--coach --samples=5]

# 盤面還原（單步/區間；失 Set 回放整段找根因）
npm run analyze:replay -- --file=... --board=29   # 或 --board=22-30

# 全場逐手 coach 掃描（~0.3s/步；輸出「實際 vs 建議＋勝率差」清單）
npm run analyze:replay -- --file=... --coach --samples=5 --threshold=0.15

# 單步 coach 深掘（便宜做 samples=25/50）
npm run analyze:replay -- --file=... --coach-step=80 --samples=25

# 單場一致率回寫 matches.jsonl（供 anchor:trend）
npm run analyze:replay -- --file=... --anchor --samples=5 --verify-samples=25

# 趨勢與牌組模擬
npm run anchor:trend
npm run analyze:m8 -- --deck="X" [--compare-deck="X_變體"] --preset=formal|holdout --opponents="A,B,C"
```

**成本感**：coach/anchor 掃描約 0.3–0.4 秒/決策步（samples=5），一場 100–130 步 ≈ 40–60 秒；71 場全量批掃約 10 分鐘。samples=25 約 ×5。**全量批掃是可日常負擔的操作**，不要因為「感覺很貴」而只挑一場看。

### A3 建議工作流（三種粒度）

1. **單場復盤**（原設計）：SKILL.md 的階段 0（triage）→ 階段 1（單手深掘）→ 寫報告＋lesson。推理等級：triage＝中、深掘＝高。
2. **跨場模式歸納**（本次新增、報告 17/18 的做法）：批次跑 macro＋coach → 把 findings 按（實際→建議）文字對正規化、統計重複模式 → **只採信「跨場重複 ≥5 次的模式」** → 對代表個案跑 samples=25 復驗 → 對存活個案 `--board` 深掘。批掃與彙整腳本在本次 scratchpad 已驗證可行（見 §B9 建議轉正為工具）。
3. **牌組調整迴圈**：跨場歸納找出結構性弱點（如「未能登場」佔失 Set 6 成）→ 開 2–3 個變體 JSON 放 `data/decks/` → `analyze:m8 --compare-deck` formal → 優勝者跑 holdout 複驗 → 實戰 3–5 場定案。**警語：deck-analyzer 的 heuristic 政策不宣告技能，技能依賴卡的價值被系統性低估**——模擬結論只對「身體值/登場合法性/事件密度」類改動可信，技能卡的增減必須實戰驗證。

### A4 可使用場景（含你可能沒想到的）

- **賽前特定對手 gameplan**：把 vs 某對手的所有 replay 批掃 macro，看失 Set 歸因與 OP/DP 曲線，10 分鐘產出「這個對手怎麼打」的數據頁（報告 17/18 的 §1 就是這樣長出來的）。
- **AI 迴歸監測**（已內建但容易忘）：每次動 value model / search 之前，`anchor:trend` 按 engineVersion 分組的一致率就是免費的迴歸尺。⚠️ 呼應既有備忘：**下次換 value model 前先凍結 so-k-v1 快照**。
- **「AI 漏洞表」自動萃取**：報告 08 §4 的「AI 極少預留接6」是手工觀察；同樣的問題可以批掃回答——對 AI 座位（`--player=1`）跑 coach/macro，統計它的防守登場分佈。給 AI 開發側（Phase H/K/L）當行為指標，跟 M-Throw 系列互補。
- **lessons 庫的對局中喚起**：目前 lessons 只在復盤時 grep。UI 對局中若在同型局面（卡號＋phase 命中）彈出「L0004：這筆交換率划算嗎」，記憶層就從事後變事中（M9 UI 的候選需求）。
- **每週自動週報**：schedule 一個 routine：掃新 replay → 補 anchor → anchor:trend → 產 3 行摘要（勝率窗、一致率、新增 blunder 熱點）。
- **教學素材**：reports/ 已累積 19 篇，體例穩定（表頭含 seed/資料來源/分析者），可以直接彙編成「這套牌的教科書」。

## B. 優化建議（按嚴重度排序）

### B1【bug，已定位】巨觀戰報的「技能」統計恆為 0
`src/ai/replay-review.ts` `buildActionCardDetails()`（約 :198）用 log 前綴「`使用 X 的技能`」偵測技能宣告，但引擎實際寫的是「`解決：X 的技能`」「`解決：X 的登場技能`」（另有「選擇不使用技能」＝decline）。**結果：71/71 場戰報全部顯示「技能: 本場未使用」**，技能效率面板從未工作過。修法：改比對「解決：」系式樣，排除「不使用」「無效」；`buildActionCardDetails` 與 `buildActionEffectiveness` 有 consistency test 交叉驗證，改一邊要同步。（已開背景任務 chip：「修復 replay-review 技能統計恆為 0 的 bug」。）

> [Codex 2026-07-07] 已修：benchmark / replay-review 改以 decision-layer usage 補足事件 / 技能 uses，待機被動技能也會納入逐卡明細；全測 816 綠。注意：實作選擇比原建議更靠近 replay decision source，而不是只補 log regex。
>
> [Claude 2026-07-07] 復測後補完：Codex 的 decision-layer 修法涵蓋自由步驟宣言型（`free/skill`）與待機被動（`resolve-pending`），但**漏了 gate 技能主路徑**——登場/區域技能走「log『解決：X 的(登場)技能』→ 下一個 effect-confirm/effect-cards 決策」，而 gate 的 pendingDecision 不帶來源卡 uid，兩套主力牌組的技能 9 成走這裡，修後仍顯示 0。已補：(1) 以「解決：」行為 pending 上下文、與同玩家下一個 gate 決策配對計數（accept／非空選卡＝use；decline／空選＝不計；「選擇不使用技能」與事件打出時清除防誤配）；(2) 關鍵字效果 log「［フェイント(4)］」等納入 impact（修正国見 041 被判無效）。復測 71 場：youth 技能 5.5 次/場（影山 93%、星海 93%、宮侑 86%）、aoba 6.7 次/場（99% 有效）。**殘留限制**：遲發效果（「解決：X 的遲發效果」）不回溯歸因到來源技能——古森 028 顯示 3% 有效是假象，實際 cost→payoff 兌現 30→24 次（80%）；接手者若要精確，需在 watcher 註冊時記 source 對照。817 tests 綠。

### B2【方法論】samples=5 的 finding 留存率僅 27–39% → anchor blunderCount 高估約 3 倍
兩場代表局用 samples=25 復驗：youth 場 22 筆 finding 只剩 8 筆（留存 27%）、aoba 場 33→18（39%）。samples=5 時勝率差的最小刻度就是 20%，threshold=0.15 幾乎把單樣本抖動全收進來。影響：`matches.jsonl` 的 blunderCount（每場 20–35）真值大概在 6–12；一致率（top1 相同與否）受影響較小但也有噪訊。建議：
- anchor 掃描改**兩段式**：samples=5 全掃篩候選 → 對候選步 samples=25 復驗，只有存活者計入 blunderCount；
- `matches.jsonl` 補 `samplesUsed` 欄位（現在只有 blunderThreshold），否則跨版本趨勢會把「掃描設定變更」誤讀成「人變強/變弱」。

> [Codex 2026-07-07] 已實作：`--anchor` 預設 `--samples=5 --verify-samples=25`，blunderCount 寫復驗存活數；JSONL 會記 `samplesUsed`、`blunderVerificationSamples`、`blunderCandidates`。一致率仍使用第一階段全掃結果，因為它要維持完整分母。

### B3【可疑的引擎偏差】防守選擇建議系統性偏向「攔網」
「玩家選接球 → 建議選攔網」youth 36 次＋aoba 31 次。抽出全部 67 個現場：**對手 OP≤3 的占 26 個、玩家手牌 5 張的占 38 個**——不是「打不過才勸縮」。旗艦反例（samples=25 存活）：aoba S4T3 對手 **OP=1**、場上金田一接2 白接，搜尋仍給「攔網 76% vs 接球 28%」。規則面（`engine.ts` block 流程）：攔網成功 → 算出 block OP（基準0）→ **直接進 end phase，跳過自己整輪托/攻反擊**；接球成功還多抽 1 張。tempo 上接球明顯占優，此建議缺乏機制合理性。候選根因：value 對「放棄反擊回合」的機會成本失明（與 L0007 技能點失明同族，Phase H W2/W3 的近親）、或與「勸棄局」邏輯糾纏（選攔網後不登場＝變相棄局保手牌）。**建議專項調查**：從這 67 個盤面各做 forced-choice rollout A/B，量化兩線真實勝率差；在修復前，復盤分析遇到此類建議一律標「引擎已知疑點」。

### B4【校準】「主動 Lost」勸棄建議過度悲觀——實戰逆轉率 >50%
「AI 建議主動 Lost、玩家續打」youth 59 段（續打贏 31）、aoba 66 段（贏 36）。即使考慮對手也是同一顆引擎（互相放水部分抵銷），>50% 的逆轉率仍表示勸棄線的價值估計顯著偏低。已寫入 lessons **L0008【AI行為】**提醒後續復盤者：勸棄建議要過「續打成本 ≤2 手牌」的人工準則再採納。這與 B3 可能同根（grind 線的長期價值被低估）。

### B5【UX】coach label 無法區分同名卡的版本與付款來源
「登場 及川 徹（28%）→ 建議 登場 及川 徹（68%）」這類輸出（aoba 34 次、youth 17 次，且平均勝率差最大）人類無法讀。實情是 033/056/058/PR-024 四種及川或不同 Guts 付款的差異。建議 label 帶卡號尾碼與區位：「登場 及川 徹〔058〕」「支付 Guts〔接球區〕」。這是低工作量高回報的修改（`coach.ts` 的 label 生成處）。

> [Codex 2026-07-07] 部分完成：`coach.ts` 的卡名 label 已補短卡號尾碼（例：`及川 徹〔058〕`），並有測試鎖住；付款來源尚未補，因為需追 effect-cost 選卡上下文，留給後續專門處理。

### B6【UX】coach 解釋是決策類別模板，非局面特定
所有 deploy 建議的解釋都是「此選項主要在提高本回合 OP/攻擊線壓力」等固定句式，samples=25 時照樣說「目前樣本仍偏少」（門檻沒跟 samples 連動）。K3 的 explainValue 已在 UI 端接線，CLI 的 coach 文字尚未吃到。建議：解釋至少帶出「兩線在 rollout 中的分歧點」（如：建議線下一回合可多守一波 OP6）；「樣本偏少」措辭改依 samples 動態。

### B7【工具缺口】沒有單步 coach
深掘第 80 步要 `--max-coach-steps=80` 掃完整段前綴。加 `--coach-step=N`（或 `--board=N --coach` 組合語義）只評那一步、順便支援 `--samples=50` 的高精度單點，會讓 SKILL.md 階段 1 的「對該步跑 PIMC」便宜 50 倍。

> [Codex 2026-07-07] 已實作 `--coach-step=N`，指定後自動啟用 `--coach`，只評估 replay 全域第 N 步；已用實際 replay smoke 驗證。

### B8【表達力缺口】gameplan objective 缺「事件區張數」型別
`gameplan.ts` 的 ObjectiveType 只有 uniqueDropNames/keyCardZone/resourceReady/opponentHandPressure/activeWatcher。ユース的「事件區燃料 ≥1」與青葉城西 P03 的「事件區 ≥4 gate」都無法表達（兩套牌的核心資源軸！）。建議加 `eventAreaCount`（自己事件區張數，含 affiliation filter）。**本次已補上兩套牌組缺失的 profile v1**（`youth-camp-elite-v1`、`aoba-johsai-p03-test-v1`，見 `data/gameplans/profiles.json`；gameplan tests 7/7 綠、814 全測綠）——但受限於此缺口，燃料軸只能用 resourceReady(Guts) 近似，接手者加了新型別後請回頭升級這兩個 profile。

### B9【流程】把本次批掃管線轉正
本次的「全 replay 批掃＋（實際→建議）模式彙整」是臨時 scratchpad 腳本。建議轉正為 `tools/batch-replay-scan.ts`：輸入牌組名 → 自動對其全部 replay 跑 macro＋coach → 輸出 JSON 彙整（含 by-phase 分佈、重複模式 top N、與 macro set 結果的交叉）。這會把「報告 17/18 等級的跨場復盤」從一次性工程變成一條命令。另外：gameOver 記錄 human-anchor 時，若該牌組沒有 gameplan profile，順手提示一行「建 profile 才有主軸覆盤」。
