## 0 規則前提（先釘死）
- **技能 gate 是可選的**（`effect-confirm` accept/decline）。引擎跳出 gate＝該技能**條件已滿足、可使用**；decline＝放棄該效果。
- **同名覆蓋**：攻擊區可再登場角色覆蓋既有攻擊手，被蓋者落為 Guts。攻擊≠托球同名限制仍在（本手托球＝木葉、攻擊＝木兎，無衝突）。
- **OP（attack source）＝托球區頂端 toss ＋ 攻擊區頂端 attack**（`engine.ts:calcOp`，引擎權威值，直接讀 `state.op`，不自行重算）。

## 1 核心結論
**放水屬實，且是「價值/gate 判斷看不到技能點數」的系統性問題，非偶發。** 在 Set 2 一個進攻回合（電腦**並未領先**），電腦把站著的木兎[攻3]用木兎[攻0, HV-P01-043]覆蓋，引擎跳出該卡「攻擊+5」技能 gate（條件「全員梟谷」已滿足、**無 Guts 成本**），**電腦卻 decline**，導致 OP 算出＝**0**。最佳線是接受 +5→OP 5（或根本不覆蓋、保留 OP 3）。全場電腦進攻 OP＝4/0/0/2/8，爆發牌組平均 OP 僅 **1.88**（玩家 3.60）。

## 3 為什麼（卡值＋系統性掃描）
- **HV-P01-043 木兎技能**：「[=登場][=アタックエリア] 從手牌登場、全員梟谷、攻擊區 Guts 為奇數時可使用。**攻擊點數 +5**。」——無 Guts 成本的純增益。電腦場上全員梟谷→條件滿足（gate 有跳）。接受＝攻0→攻5、OP 0→5。
- **這不是孤例。電腦全場 gate 決策**：

  | 時機 | accept? | 後果 |
  |---|---|---|
  | S1T4 block | **False** | 防守技能沒開（無防守壓力） |
  | S2T2 attack | **False** | 本手：拒 +5 → OP 0 |
  | S2T4 toss | **False** | 托球技能沒開 |
  | S2T8 receive | True | — |
  | S3T4 toss×2 / attack | **True** | → OP 8、贏 Set 3 |

  模式：**Set 1–2 落後/拉鋸時一路拒絕有利免費技能；S3T4 才接受 → 爆 OP 8。** gate-confirm 偏向拒絕、且不穩定。
- **關鍵：拒絕都發生在「電腦沒領先」時** → 排除「領先就擺爛（H-W1 飽和）」；根因＝**價值函數/gate 判斷看不到技能帶來的攻防點數（H-W2/W3）**，把免費 +5 當「不值得」。對應 Phase H spec（`docs/M8_PHASE_H_PLAY_QUALITY_SPEC.md`）的 H-W2（看不到攻擊點數）＋H-W3（低估技能/防守增益）。

## 4 建議打法＋誠實評估
- **本手正解**：覆蓋後 accept +5 → OP 5（toss0+attack5）；或更省＝不覆蓋、保留木兎[攻3] → OP 3。實際 OP 0 為嚴格劣解。
- **修法方向**：屬引擎 AI 問題，非使用者打法。最直接＝gate-confirm 評估要看到「接受後 OP/DP 的實際變化」（目前 heuristic「高成本低收益可拒絕」把零成本 +5 誤判為低收益）；根本＝Phase H 補攻防點數特徵＋重 fit。**先做 H0 行為指標量基準**（M-Throw1 低點攻擊率、M-Throw2 技能怠用率），再驗修正。
- **誠實天花板**：本場是 vs-heuristic（弱機器人）視角的「品質」問題，不是強度問題——電腦放水仍可能贏弱對手；本局玩家 3:1 勝，正說明「勝率高 ≠ 打得像高手」。
